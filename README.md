# agent-eval

과제와 협업 조건을 주입하고, 에이전트의 수행 성능과 평가 신뢰성을 반복 측정하는 실험 도구입니다.

**상태: 프로젝트 방향성과 개발 철학을 확정했습니다. 실행·평가 기능은 아직 구현하지 않았습니다.**

## 목적

에이전트의 모델·프롬프트·스킬·역할 구성·협업 방식 변경이 과제 수행에 미치는 영향을 같은 기준과 증거로 비교합니다. 단일 과제부터 여러 역할이 협력하는 파이프라인까지 평가하며, 프로젝트가 달라도 실험·증거·판정·비교 절차를 재사용합니다.

핵심 질문은 세 가지입니다.

- 주어진 과제를 얼마나 정확하고 일관되게 완수합니까?
- 역할 간 분담·인계·검토·통합이 전체 목표 달성에 기여합니까?
- 조건 변화와 장애에 어떻게 대응하며, 개선에 시간과 비용이 얼마나 듭니까?

## 제품 방향

| 구성 | 책임 |
| --- | --- |
| 과제 묶음 | 입력 자료·허용 행동·필수 산출물·완료 조건·평가 기준·출처·버전을 정의합니다. |
| 실험 명세 | 가설·비교군·대상 시스템·역할 구성·반복 횟수·예산·변경 조건을 고정합니다. |
| 협업 시나리오 | 순차 인계·병렬 분담·통합·검토 후 수정과 단계별 관찰 지점을 정의합니다. |
| 조건 주입 | 과제·추가 자료·요구사항 변경·도구 실패·인계 누락을 지정된 지점에 적용합니다. |
| 증거 수집 | 입력·응답·도구 호출·산출물·실행 상태·버전·측정값을 연결해 보존합니다. |
| 평가와 비교 | 규칙 검사·의미 평가·사람의 검토를 구분하고, 반복 결과와 변경 전후 차이를 보고합니다. |

과제의 분야와 난이도는 과제 묶음에서 확장합니다. 공통 엔진에 특정 직무나 특정 모델의 판정 기준을 내장하지 않습니다. 초기의 작은 과제 묶음은 기능과 평가 기준을 검증하기 위한 자료이며, 광범위한 성능을 대표하지 않습니다.

## 개발 철학

1. **증거와 판정을 분리합니다.** 실행 원본을 보존하고 판정은 별도 버전으로 추가합니다. 저장된 증거가 충분하면 모델을 다시 실행하지 않고 재평가합니다.
2. **실행 완료와 과제 성공을 구분합니다.** 정상 종료·형식 충족·내용 충족·전체 목표 달성을 별도로 기록합니다. 실행 실패, 판정 불가, 평가기 오류도 구분합니다.
3. **평가 도구 자체를 검증합니다.** LLM 판정은 근거가 있는 평가 의견으로 저장합니다. 사람이 확정한 기준 사례로 오탐·미탐과 일치도를 확인하며, 불일치는 원래 판정을 보존한 채 검토합니다.
4. **비교 조건을 결과보다 먼저 고정합니다.** 과제·입력·기준·대상 버전·모델 설정·예산·반복 횟수를 기록합니다. 변경된 조건과 누락된 정보는 보고서에 명시합니다. 같은 설정이 같은 모델 출력을 보장한다고 가정하지 않습니다.
5. **미측정과 불확실성을 보존합니다.** 누락된 비용·시간·토큰은 사유와 함께 미측정으로 남깁니다. 제외·실패·보류 건수와 지표의 분모를 공개합니다. 임의의 종합 점수를 기본 성과로 사용하지 않습니다.
6. **협업의 효과를 검증합니다.** 같은 과제와 비교 가능한 자원 예산에서 단독 수행과 협업 수행을 비교합니다. 역할 수·호출 수·검토 횟수 자체를 성과로 취급하지 않습니다.
7. **작게 완결하고 재사용으로 일반화합니다.** 하나의 실험을 끝까지 구현한 뒤 두 번째 과제 묶음으로 계약을 검증합니다. 독립 배포 필요가 확인되기 전에는 모듈을 별도 서비스나 저장소로 분리하지 않습니다.
8. **실험 기록을 덮어쓰지 않습니다.** 재시도·재실행·재평가를 구별합니다. 실패와 중단 기록을 남기며, 외부 작업의 실행 여부가 불확실하면 자동 재실행하지 않습니다.

## 프로젝트 경계

agent-eval은 실험 명세, 평가용 시나리오와 주입 계획, 증거 계약, 판정과 비교를 소유합니다. 실험 실행 요청과 반복 조정은 실행 어댑터를 통해 수행합니다. 업무 흐름의 실제 스케줄링·역할 세션·워커 관리·복구 정책은 실행 시스템이 소유합니다.

| 연결 대상 | 소유 책임 | agent-eval의 연결 방식 |
| --- | --- | --- |
| [codex-adapter](https://github.com/shakystar/codex-adapter) | Codex 프로토콜·세션·호출 실패 정보 | 실행 어댑터를 통한 결과 수집 |
| [role-runtime](https://github.com/shakystar/role-runtime) | 실행 슬롯·역할 상태·영수증·산출물 | 실행 사실과 결과물 참조 수집 |
| [role-orchestrator](https://github.com/shakystar/role-orchestrator) | 작업 의존성과 흐름·인계·재개 | 시나리오 전달과 실행 기록 회수 |
| [skill-search-engine](https://github.com/shakystar/skill-search-engine) | 검색·스킬 버전·검색 관련성 기준 | 과제별 평가 모듈 또는 실행 대상 연결 |

위 연결은 개발 방향이며 구현 완료를 의미하지 않습니다. 특정 실행 시스템 없이도 저장된 증거를 평가할 수 있어야 합니다. 대상 저장소의 내부 코드를 직접 가져오지 않고 버전이 명시된 공개 계약으로 연결합니다.

공통 계약과 작은 기준 사례는 이 저장소에서 관리합니다. 프로젝트 고유 과제와 평가 기준은 해당 프로젝트가 소유하고, 실험에서는 정확한 버전이나 해시를 참조합니다. 공통으로 유지할 가치가 확인된 과제 묶음은 이 저장소에 포함할 수 있습니다.

관측 서비스는 선택적으로 연동합니다. 관측 데이터의 수신이나 역할의 자체 완료 선언만으로 과제 성공을 판정하지 않습니다.

## 실험과 평가의 원칙

- 각 주입은 대상·내용·시점 또는 트리거·실제 적용 여부를 기록합니다. 지원하지 않는 주입은 명시적으로 거부하고, 미적용 실험을 적용된 실험처럼 집계하지 않습니다.
- 평가용 정답과 숨겨진 기준은 수행 에이전트의 입력에서 분리합니다. 기준 조율 자료와 최종 검증 자료도 구별합니다.
- 산출물 품질과 협업 과정을 함께 확인합니다. 과정 기록이 부족하면 확인 가능한 범위만 판정합니다.
- 형식·필수 필드·참조 무결성은 가능한 범위에서 기계적으로 검사합니다. 의미 판단에는 기준 ID와 근거를 연결합니다.
- 평가자·프롬프트·기준 버전을 남기며, 평가 기준이 바뀐 결과는 별도 계열로 관리합니다.
- 반복 결과에는 표본 수와 분포를 함께 제시합니다. 단일 성공과 합성 검사를 실제 과제 전반의 성능으로 확대 해석하지 않습니다.
- 실행 원문과 비공개 과제는 기본적으로 로컬에 보존합니다. 공개 저장소에는 공개 가능한 과제와 정제된 근거만 포함합니다.

초기 지표는 다음 범위로 제한합니다.

| 축 | 지표 |
| --- | --- |
| 과제 수행 | 항목별 충족률·전체 성공률·반복 성공률 |
| 협업 | 필수 정보 인계율·근거 보존·중복 작업·의존성 및 상충 결과 처리 |
| 복구 | 장애별 복구 성공률·복구에 추가된 실행과 시간 |
| 효율 | 측정 가능한 시간·토큰·비용과 측정 범위 |
| 평가 신뢰성 | 평가자 불일치율·사람의 확정 판정과의 일치율·오탐·미탐 |
| 비교 | 고정한 기준 실행 대비 변화와 반복 간 변동 |

지표별 정의·분모·제외 조건·합격 기준은 실험 전에 명시합니다. 협업에 적용되지 않는 항목은 해당 없음으로 표시합니다.

## 재사용 결정

Inspect AI의 채점·재평가·로그 API·뷰어를 첫 재사용 대상으로 선택합니다. Harbor는 환경형 과제의 실행·검증을 맡는 후속 백엔드로 둡니다. 실험 조건·인계 정책·주입 적용 기록·증거 연결·판정 확정과 비교는 agent-eval이 소유합니다.

첫 실제 실행은 기존 role-orchestrator → role-runtime → codex-adapter 경로를 유지합니다. 외부 하네스의 모델 라우팅으로 자동 교체하지 않으며, 실행과 재시도 소유자를 하나로 고정합니다. M0 계약 검증을 거친 범위만 연결하고, 기능 구현·통합 성공과 기획 결정을 구분합니다.

## 초기 구현 방향

Python 라이브러리와 CLI를 제공하는 단일 저장소의 모듈형 모놀리스로 시작합니다.

- domain: 과제·실험·증거·판정 계약을 정의합니다.
- application: 실험 조정·검증·평가·재평가·비교를 담당합니다.
- ports: 실행 시스템·평가기·증거 저장소의 인터페이스를 정의합니다.
- adapters: 외부 실행 계약·규칙 검사·LLM 평가·저장 형식을 연결합니다.
- cli: 같은 유스케이스를 명령행으로 제공합니다.

도메인은 파일·네트워크·모델 공급자에 의존하지 않습니다. 구체적인 패키지, 저장 형식과 스키마는 첫 구현에서 결정합니다.

## 첫 개발 범위와 완료 기준

첫 적용 대상은 고정된 문서 과제와 작성→검토→수정 흐름입니다. 같은 과제를 단독·협업·조건 주입 상태로 비교합니다.

1. Inspect의 고정 버전 log/score 계약과 기존 실행 capability를 검증하고 과제·실험·증거·판정의 최소 계약을 정의합니다.
2. Inspect의 로그·채점 기능을 재사용하여 저장 기록 가져오기·규칙 검사·재평가·비교를 연결합니다.
3. 기존 실행 시스템에 연결해 단독 수행과 협업 수행을 반복 실행합니다.
4. 지정된 단계의 자료 추가와 도구 실패 주입을 지원합니다.
5. 사람이 확정한 기준 사례로 평가기를 확인하고 두 번째 과제 묶음으로 재사용성을 검증합니다.

다음 조건을 충족하면 첫 버전을 완료한 것으로 판정합니다.

- 실험 설정에서 실행 증거와 판정 근거까지 추적할 수 있습니다.
- 동일 증거를 재평가해도 원본과 이전 판정이 보존됩니다.
- 단독·협업·주입 조건의 차이를 정의된 지표로 보고합니다.
- 주입 미적용·실행 실패·평가 오류·미측정 항목이 결과에 드러납니다.
- 두 과제 묶음이 공통 엔진 수정 없이 과제 정의와 평가 모듈을 통해 같은 CLI를 사용합니다.
- 평가기의 판정 정확도를 확인한 범위와 남은 불확실성을 명시합니다.

웹 UI, 분산 실행, 상주 스케줄러, 동적 팀 생성, 자동 자기 개선, 대규모 과제 카탈로그는 첫 범위에 포함하지 않습니다.

## 문서와 변경 관리

이 README를 프로젝트 진입 문서이자 방향성의 기준으로 사용합니다. 목적·책임 경계·평가 원칙을 바꿀 때에는 변경 이유와 영향을 기록합니다. 이후 AGENTS.md에는 진입 문서·작업 제약·필수 검증만 두고, 작업별 상세 절차는 프로젝트 스킬로 분리합니다.

구현 상태, 합성 검사, 실제 모델 실행, 평가 신뢰성 검증은 각각 구분해 기록합니다. 이 문서의 완료 기준은 향후 검증할 기준이며 현재의 실행 결과가 아닙니다.
