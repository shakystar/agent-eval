# M3 실행 및 주입 검증

**M3 완료 (2026-11-20).** Docker Linux 실모델에서 계획된 네 조건을 두 번씩 완료했고, 별도 검사에서 수정과 최종 수락까지 확인했다. 아래 첫 표의 macOS 결과는 기본 DNS에서 수행한 기존 실험이다. [Linux 실모델 실행 증거](m3/linux-results.json)

2026-11-20. 합성 결제 점검 공지를 과제로 고정하고 단독 작성, 협업 검토, 검토 자료 추가, 검토 직전 인계 읽기 실패의 네 조건을 두 번씩 실행했다. 실험의 산출물 규칙은 `has-notice`(비어 있지 않은 출력) 하나다. 공지의 사실 정확성이나 협업 효과에 대한 사람 판정은 이 실험에서 수집하지 않았다.

| 조건 | Docker Linux fixture | macOS 실제 Codex | 실제 조건 적용 |
| --- | --- | --- | --- |
| 단독 작성 | 2/2 완료 | 2/2 완료 | 작성 단계 각각 1회 |
| 작성 → 검토 | 2/2 완료 | 1/2 완료 | 첫 반복은 검토 수락, 둘째는 작성 전에 중단 |
| 검토 자료 추가 | 2/2 완료 | 2/2 완료 | 두 검토 요청에 각 1회 적용, 두 건 모두 수락 |
| 인계 읽기 실패 | 2/2 완료 | 1/2 완료 | 첫 반복 미적용, 둘째는 일시 실패 1회 후 같은 문서 읽기 성공 |

**실행 동일성(C-05).** Linux fixture는 고정 role-orchestrator `5d2b518`, role-runtime `2be08fc`를 사용했다. macOS 실모델은 `50bf7a9`, `bba4f3a`와 runtime의 codex-adapter Go 의존성 `3ab5b920bf6c`를 사용했다. 호스트의 기존 계정 경로를 사용했고 성공한 10개 단계의 서로 다른 세션에서 실제 턴 모델이 모두 `gpt-6.2-astra`였음을 확인했다. 등록된 역할 12개의 도구 프로필은 모두 `advisory`였다. 8개 반복의 runtime ID와 12개 단계의 시도 ID는 각각 고유했다. M2의 의미 채점 모델 설정은 이 실행에 사용하지 않았다.

**협업과 주입(C-06).** Linux fixture에서 8개 실행, 26개 단계를 완료했다. 모든 협업 반복이 작성 → 검토 → 수정 → 최종 검토를 거쳤다. 자료 주입의 전후 입력 해시가 달랐고, 인계 장애 복구 후에는 같은 문서가 전달됐다. 실제 모델의 기본 비교 실험에서는 완료된 협업 4건 모두 첫 검토에서 수락했다. 장애 대상은 어댑터가 소유하는 `read_handoff`다. 모델 내부 도구나 외부 서비스 장애는 이 실험의 대상에서 제외했다.

**실모델 수정 분기.** 기본 비교와 별도로 검토 단계에서 처음 공개하는 고객지원 참조번호 `PAY-427`을 추가 요구했다. 이 확인용으로 실행한 별도 슬롯 3개 중 2개는 작성 전 계정 조회 시간 초과, 1개는 네 단계 모두 완료였다. 완료 사례의 초안에는 번호가 없었고, 첫 검토는 번호를 명시해 수정을 요청했다. 수정 산출물에서 번호를 확인했고 최종 검토는 수락했다. 작성·수정의 작성자 세션과 두 검토의 검토자 세션이 각각 일치했다. 원본은 `artifacts/m3-validation/revision-check/`에 있다. 개발 초기 연결 확인용 단독 1회도 작성 전 계정 조회에서 중단됐으며 기본 비교 분모에서 제외했다.

**실패·복구.** macOS 비교 실험에서 중단된 2건 모두 native 영수증에 `canceled`, `account_read`, `timeout`, `execution=not_started`가 남았다. 같은 슬롯을 새 실행으로 교체하지 않았다. 회귀 검사에서는 제출 의도만 남은 강제 중단은 불확실로, 이미 성공 영수증이 생성된 뒤의 강제 중단은 완료로 복구했으며 두 경우 모두 재제출 0회였다. 완료된 fixture 슬롯은 bridge 경로를 제거하고 다시 요청해도 동일한 JSON 값을 반환했다.

**회귀와 재평가.** 네트워크를 끈 Linux 컨테이너에서 M1 20개, M2 8개, M3 7개를 모두 통과했다. fixture와 실제 실행 증거를 각각 8건씩 읽어 독립적으로 규칙 평가와 보고서 생성을 완료했다. 채점기 오류는 양쪽 모두 0건이었다. 산출물 존재 규칙은 fixture 8건, 실제 6건 충족으로 집계됐고 실제 중단 2건의 전체 결과는 판정 불가였다. 토큰과 비용은 runtime 미제공으로 미측정이다.

**초기 환경 검사.** Docker Linux에서 Codex 계정 라우팅을 이 개발 작업 중 두 번 다시 확인했으나 모두 `workspace_routing_timeout`이었다. 이 시점에는 Linux 실모델 호출까지 도달하지 못했다. macOS에서도 계정 조회가 간헐적으로 실패했다. 원인은 확정하지 못했다. [사전 검증](m3-preflight.md)

**계정 라우팅 후속 대조 (2026-11-20 04:33 UTC).** 기본 DNS에서 Go 어댑터 없이 Codex 0.170.0 app-server의 `account/read`를 직접 호출했다. macOS와 Docker 모두 두 번씩 약 15초 후 라우팅 시간 초과를 반환했다. 연결 로그의 대상은 `chatgpt.com`이었다. 호스트와 Docker 양쪽에서 같은 호스트명과 TLS 검증을 유지하고 당시 DNS의 IPv4 주소를 하나씩 선택해 비교했다.

| 목적지 | 비인증 HTTPS 검사 (호스트 / Docker) | Docker의 기존 Go 어댑터 계정 조회 |
| --- | --- | --- |
| `104.18.32.47` | 각각 2/2 HTTP 200, 모두 0.5초 이내 | 2/2 성공, `routingAvailable=true` |
| `172.64.155.209` | 각각 2/2 TCP 연결 시간 초과, 제한 5초 | 2/2 `workspace_routing_timeout` |

계정 조회 대조군은 같은 이미지, CLI, Go 바이너리와 읽기 전용 인증·설정을 썼고 일회성 컨테이너의 주소 선택만 달리했다. 이번 장애는 이 환경에서 목적지 주소에 따라 재현된다. TCP 연결이 끊기는 네트워크 구간은 특정하지 못했다. 기존 Go 프로젝트에도 11월 18일 같은 증상 기록이 있다(커밋 `2e2a0da`). 이 주소별 계정 조회 비교에서 모델 요청은 0회다.

**Linux 실모델 후속 검증 (2026-11-20 04:35 UTC).** 당시 DNS 응답에 있던 `104.18.32.47`을 일회성 컨테이너의 `--add-host`로 지정했다. 같은 컨테이너에서 Go doctor가 성공한 뒤 M3 단독 과제 1회를 실제 Codex로 실행했다. 작성 영수증은 `succeeded`, 기록된 실행 시간은 5.41초였다. 127바이트 공지에는 결제 중단 시간, 탐색 가능 여부, 재시도 시점이 담겼다. 저장 산출물이 원본 영수증과 일치했고 규칙 판정은 충족 1건, 오류 0건이었다. 별도 실행 저장소는 `artifacts/m3-validation/linux-pinned-solo.z69XOm/`이다. 위 8회 비교 실험은 원래 분모를 유지한다.

실험 입력, 원시 영수증, 실행 저장소와 보고서는 로컬 `artifacts/m3-validation/` 아래의 `fixture-final`, `live-check`에 보존했다. [재현 방법](../m3-execution.md)

## Linux 실모델 완료 검증

기존 단독 1회의 실행 저장소와 실험 명세를 그대로 사용해 남은 7회만 제출했다. 동일한 Linux 이미지에서 실제 Codex CLI 0.170.0을 사용했다. 실행 컨테이너에만 당시 응답한 DNS 주소를 적용했다.

| 조건 | 완료 / 계획 | 영수증과 인계에서 확인한 내용 |
| --- | --- | --- |
| 단독 | 2/2 | 반복마다 독립 작성 세션에서 산출물 생성 |
| 협업 | 2/2 | 첫 검토에서 수락, 검토 입력의 문서 해시가 작성 출력과 일치 |
| 자료 주입 | 2/2 | 검토 요청에 자료를 각 1회 추가, 주입 전후의 다른 입력 필드는 동일 |
| 인계 읽기 장애 | 2/2 | 검토 직전 일시 오류 각 1회, 같은 해시의 문서를 다시 읽어 검토 완료 |

별도의 1회 수정 검사에서 검토 단계에 처음 공개한 `PAY-427`이 초안에 없음을 확인했다. 검토자가 수정을 요청했고, 작성자가 기존 세션에서 번호를 추가한 뒤 기존 검토자가 최종 수락했다. 이 검사는 위 표의 8회와 별도로 집계했다.

**C-05와 C-06 통과.** 9개 실행의 18개 단계 모두 실제 요청·영수증·저장 출력이 일치했다. 단계별 시도 ID는 고유했고, 16개 역할 세션은 실행 간에 공유되지 않았다. 등록된 도구 프로필은 모두 `advisory`였다. 이번에 실행한 17개 턴(15개 역할 세션)의 실제 모델은 모두 `gpt-6.2-astra`였다. 이전 단독 1회의 모델명은 당시 세션 로그를 보존하지 않아 미확인으로 남겼다.

네트워크를 끈 별도 컨테이너에서 실행 바이너리 경로를 제거하고 9건을 다시 조회했다. 반환한 결과, 실행 의도, 원본 영수증과 시도 기록이 모두 같았다. 저장된 증거의 산출물 존재 규칙은 비교 8건과 수정 1건을 충족으로 판정했고 채점기 오류는 0건이었다. M1 20개, M2 8개, M3 7개 회귀 검사가 모두 통과했다. 검증 이미지와 작업 트리의 Python 소스·테스트·예제도 일치했다.

실행별 산출물과 영수증 해시는 [검증 결과 JSON](m3/linux-results.json)에 기록했다. 전체 원본과 오프라인 보고서는 로컬 `artifacts/m3-validation/linux-pinned-solo.z69XOm/completion/` 및 상위 실행 저장소에 있다.

## 코드 리뷰 후 회귀 검증

리뷰에서 재현한 중복 제출, 늦은 영수증, 직렬화 프레임 초과, 실패한 인계 복구, 손상된 검토 증거, fixture 문자열 보존을 회귀 검사에 추가했다. 가져온 슬롯은 실제 디스패치 전에 거부됐다. 늦게 성공한 작성 단계는 읽기 전용 대조 후 `prepared`가 되었고, 다음 `execute`가 나머지 세 단계만 제출했다. 최초 `uncertain` 기록과 당시 규칙 평가 보고서는 보존됐다.

수정 이미지에서 M1 20개, M2 8개, M3 15개가 네트워크 없이 통과했다. Docker 기본 CLI로 fixture 실행·규칙 평가·보고를 연이어 수행했다. 수정 전 Linux 저장소의 복사본에서는 bridge·Codex 없이 기존 단독 실행과 이전 8회 보고서가 원본과 같은 JSON 값으로 조회됐다. role-orchestrator의 기존 41개 검사, Go 전체 패키지 검사, Go vet 및 변경된 bridge 패키지의 race 검사도 통과했다.

보완된 Linux 실제 모델 확인은 독립 과제 1회였다. 검토에 추가한 `PAY-427`이 초안에는 없었고 같은 작성자 세션에서 수정 후 같은 검토자 세션이 수락했다. 네 단계 모두 원본 영수증의 출력과 저장 산출물이 일치했으며 규칙 채점 1건의 오류는 0개였다. 기존 비교 분모는 유지한다. 원본과 결과는 로컬 `artifacts/m3-validation/review-fixes.AxLj0i/`에 있다. [복구 및 실행 방법](../m3-execution.md)
