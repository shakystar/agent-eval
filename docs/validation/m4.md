# M4 재사용 검증

**M4와 첫 버전의 재사용 검증을 완료했습니다.** 기존 공지문과 정식 재고 묶음이 같은 엔진·CLI에서 등록, 실행, 가져오기, 평가, 재평가, 보고를 통과했습니다. M4 회귀는 모델 호출 없이 수행했습니다. 후속 [실제 Codex 실행 결과](m4/inventory-codex.md)와 [과제 타당성 검토지](m4/inventory-task-review.md)를 함께 보존합니다.

## 재고 대사·보충 결정

[`inventory-reconciliation@1`](../../bundles/inventory-reconciliation/v1/bundle.json)은 원장과 발주 정책을 공개 입력으로 제공합니다. 가용 재고는 기초 수량에 입고를 더한 뒤 출고와 파손을 차감한 수량입니다. 가용 재고가 3개 미만이면 목표 7개까지 발주합니다. 세 과제는 같은 정책에 서로 다른 원장을 사용합니다.

| 과제 | 원장 대사 | `available` | `reorder` | `order_units` |
| --- | --- | ---: | --- | ---: |
| `inventory-a` | 8 + 3 − 8 − 2 | 1 | `true` | 6 |
| `inventory-b` | 6 + 4 − 5 − 2 | 3 | `false` | 0 |
| `inventory-c` | 9 + 5 − 4 − 1 | 9 | `false` | 0 |

기존 Inspect `json_equals`가 각 필드의 값과 JSON 자료형을 채점합니다. 세 기준이 모두 충족되어야 해당 산출물이 충족입니다. 원장과 정책, 평가 전용 파일은 manifest의 SHA-256으로 고정합니다. 이 묶음은 공개된 합성 보정 자료이며 세 과제의 타당성은 모두 `unreviewed`입니다.

### 일반 실험

저장소 루트에서 다음 명령으로 과제와 [단독 실행 실험](../../bundles/inventory-reconciliation/v1/experiment.json)을 등록하고 에이전트에게 제공될 입력을 조회합니다. 이 세 명령은 모델을 호출하지 않습니다.

```sh
agent-eval --store ./store bundle bundles/inventory-reconciliation/v1/bundle.json
agent-eval --store ./store experiment bundles/inventory-reconciliation/v1/experiment.json
agent-eval --store ./store input inventory-reconciliation-v1-codex inventory-b
```

실험은 세 과제를 각 1회 실행하도록 정의합니다. Linux 실행 환경에서 `execute inventory-reconciliation-v1-codex inventory-b solo 1`은 해당 슬롯에 실제 Codex 작업을 제출합니다. fixture 회귀의 결과는 아래에 별도로 기록합니다. [실행 환경과 영수증 조회](../m3-execution.md)

## 공통 CLI 회귀 재현

저장소 루트의 Linux/WSL 셸에서 실행합니다. [M3 이미지 빌드 절차](../m3-execution.md#linux에서-예제-실행)로 준비한 기본 태그는 `agent-eval-m3:dev`입니다. 아래 명령은 실행 당시 이미지 ID를 고정하고 새 저장소에 결과를 작성합니다. 출력 디렉터리는 이미지 사용자에게 쓰기 권한이 있어야 합니다.

```sh
mkdir -p artifacts
result=$(mktemp -d "$PWD/artifacts/m4.XXXXXX")
image=$(docker image inspect agent-eval-m3:dev --format '{{.Id}}')
docker run --rm --pull=never --network none \
  --mount "type=bind,source=$PWD,target=/repo,readonly" \
  --mount "type=bind,source=$result,target=/out" \
  --entrypoint python "$image" /repo/tests/validate_m4.py /out
```

[`validate_m4.py`](../../tests/validate_m4.py)는 두 묶음을 같은 빈 저장소에 등록합니다. 각 과제의 첫 반복은 fixture bridge로 실행하고 나머지 반복은 저장 산출물로 가져옵니다. 최초 평가와 자식 재평가 후 `summary.json`에 슬롯별 결과, 항목별 판정, 최초 평가와 영수증 해시를 남깁니다. 전체 저장소와 두 평가의 JSON·Markdown 보고서는 출력 디렉터리에 남습니다.

| 과제 묶음 | 실행 / 가져오기 | 계획 | 충족 | 미충족 | 판정 불가 | 평가당 항목 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 결제 점검 공지 | 1 / 2 | 3 | 1 | 1 | 1 | 3 |
| 재고 대사·보충 | 3 / 21 | 24 | 3 | 18 | 3 | 72 |

재고 각 과제에는 고정 fixture 출력, 키 순서가 다른 정답, 반대 발주 결정, 잘못된 수량, JSON 자료형 오류, 깨진 JSON, 수집된 빈 응답, 미수집 응답을 사용했습니다. 발주점에서 발주하라는 응답은 재고 수량만 충족했고, 올바른 발주 보류는 세 기준을 모두 충족했습니다. 수집된 빈 문자열은 미충족, 미수집 응답은 판정 불가로 집계했습니다. 작성된 사례별 기대 판정과 최초·재평가 결과가 모두 일치했고, 채점 오류는 0건이었습니다. [항목별 CLI 실행 결과](m4/cli-results.json)

실행 입력은 공개 과제 정의와 원장·정책을 대조했습니다. fixture 전송 요청에는 동작을 재현할 고정 응답도 들어가므로 실제 요청과 영수증의 입력을 함께 검사했습니다. 재고 fixture의 고정 응답은 세 원장 모두에서 오답입니다. 이 회귀는 배포용 Codex 실험의 등록·입력 조회까지 확인했습니다. 후속 실제 실행 3건은 별도 실험 결과로 집계했습니다.

## 검증 환경

2026-11-22에 WSL Docker/Linux의 네트워크를 차단하고 고정 M3 이미지를 사용했습니다. 이미지의 `agent_eval/*.py` 15개와 실제 CLI 진입점의 소스 해시가 기준 커밋 `7e0b6f8`과 일치했습니다. 해당 이미지에서 M1·M2 회귀 검사 48개, CLI 검사 10개, M3 회귀 검사 15개가 통과했습니다. 장애 인계의 기존 실모델 응답 4건을 재평가해 사람 기준과 4/4 일치했으며 새 모델 호출과 자동 확정은 0건이었습니다. [이미지·소스 해시와 검사별 결과](m4/baseline-regressions.json)
