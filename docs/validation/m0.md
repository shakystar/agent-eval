# M0 재사용 계약 검증

후속: [Windows 오류 수정](m0-windows-fixes.md)에서 Inspect native 실행 성공과 workflow Windows 빌드 복구를 확인했습니다. 아래 초기 실패 결과는 이력으로 유지합니다. Windows workflow 실행 지원은 여전히 별도 범위입니다.

2026-11-20. 이 검증은 라이브러리·기록 계약의 호환성 검사입니다. 에이전트 성능이나 직군 스킬의 효과를 측정하지 않습니다. 실행 결과는 [기계 판독 기록](m0-results.json)에 보존합니다.

## 결과

선택한 **사후 평가 경로의 M0 fixture 계약은 통과**했습니다. 실제 업무 실행 통합과 평가 신뢰성 검증은 완료되지 않았습니다.

| 항목 | 확인 결과 |
| --- | --- |
| C-01 | 정상·오류·중단·미채점·부분 점수의 native log 저장/읽기, 중복 식별·내용 충돌 거부 통과 |
| C-02 | 두 기준의 점수와 append 판정, 이전 파일 SHA-256 보존 통과 |
| C-03 | 실제 `score()`의 ValueError 발생, 외부 실행 fixture 재호출 0회 |
| C-04 | 계획/실행 4, 판정 가능 2, 미채점 1, 평가 오류 1; native accuracy 1/2, 계획 성공률 1/4 |
| C-05~06 | 공개 계약·소스 capability 대조 완료; 실제 모델·협업·주입 검증 미완료 |
| C-07 | 공개 입력에 비공개 canary 없음; 로그의 task_file 미실행, endpoint 연결 차단 상태에서 읽기 통과 |
| 기존 bridge | Python 계약 검사 3개와 Go 요청 vector 26개 통과; 합성 성공 receipt의 native log 변환·채점 통과 |

fixture 호출 6회는 기본 사례 4개, 부분 점수 1개, 점수 없음 1개입니다. 실제 Go 작업이나 Inspect solver 호출이 아닙니다. 외부 모델 호출은 0회입니다. 수치는 agent 성능 점수가 아닙니다.

Inspect 전체 `eval()`도 별도 시도했습니다. 현재 Windows 실행 환경에서 초기 시도에 AF_UNIX 제어 소켓 경고가 있었고, 로그 버퍼 SQLite의 `unable to open database file`로 solver 실행 전 실패했습니다. [재현 코드](../../experiments/m0/native_eval_probe.py)와 [별도 결과](m0-native-eval-results.json)를 남겼습니다. 이 결과만으로 모든 Windows 환경에서의 Inspect 지원 여부를 단정하지 않습니다. 내부 코드·잠금·권한을 수정하지 않았습니다. `native_eval_probe.py`는 실패를 JSON으로 기록하며, 명령 종료 코드 0을 eval 성공으로 해석하면 안 됩니다.

따라서 native 실행 하네스 도입은 보류하고, 원래 명세의 저장 증거 → Inspect log/score 경로만 채택합니다. viewer, 실제 모델, crash recovery는 이번 검증 범위 밖입니다.

## 범위와 재현

- Inspect: `ec5d110b1704a6eb31e2efedec59a12190df80e1`, MIT, Python 3.12.3, Windows.
- role-orchestrator: `5d2b51840e56284b6902e41cf76a00bc486dc3a2`.
- role-runtime: `bba4f3a6afc9b4ebc6adaf1c010feeb5a5434d2b`.
- codex-adapter: `42d568d33e2b763205336edf59f10adc0f471e4d`.

별도 Python 가상환경에 [고정 의존성](../../experiments/m0/requirements.txt)을 설치합니다. [실제 설치 버전 목록](../../experiments/m0/environment-windows-py312.txt)을 함께 보존했으며 `pip check`가 통과했습니다. Windows의 긴 pip 임시 경로 때문에 Git checkout이 실패하여 작업 폴더에 Inspect를 직접 clone했습니다. 첫 wheel 생성도 WinError 3으로 실패했고, 프로세스의 TEMP/TMP를 작업 폴더의 짧은 임시 디렉터리로 지정한 후 위 commit의 로컬 소스를 설치했습니다. 설치된 버전은 `0.3.292.dev17+gec5d110b1`입니다. 전역 Git·보안 설정은 변경하지 않았습니다.

```text
python experiments/m0/probe.py --orchestrator ../role-orchestrator --runtime ../role-runtime
```

외부 저장소도 위 commit으로 checkout합니다. probe는 실제 Inspect public API를 호출하고 기존 Python validator를 실행합니다. 원본 외부 저장소를 수정하지 않습니다. 생성하는 native 로그는 합성 데이터이며 `artifacts/` 임시 디렉터리에서 검사 후 제거합니다. 재실행 시 기계 판독 결과를 갱신하므로 Git diff로 변경을 확인할 수 있습니다.

보고서의 probe_sha256은 소스의 줄바꿈을 LF로 정규화한 UTF-8 SHA-256입니다. 원본 로그 보존 검사의 해시는 파일 바이트 그대로 계산합니다.

## 로그·점수 매핑

| 원본 | M0에서 확인하는 처리 | 제품 계약 |
| --- | --- | --- |
| eval_id, sample.id, epoch | 원본 ID 보존 | 논리 실행·시도·판정 ID와 별도로 연결 |
| 정상 C/I | roundtrip 후 원본 유지 | 필수 기준의 충족·미충족에 연결 |
| sample.error | 평가 예외와 기존 점수 확인 | 실행 실패와 평가 오류를 혼합하지 않음 |
| Score.unscored | NaN과 reason 보존 | 판단 불가 사유, 집계 제외 수 표시 |
| scorer의 None | 점수 없음 확인 | unscored와 별도 상태 |
| 앞 scorer 성공, 뒤 scorer 실패 | 앞 점수와 error 공존 확인 | 부분 판정이며 전체 성공 아님 |
| error/cancelled 로그 | native 저장·읽기 상태 보존 | 실패·중단 상태 유지 |
| 동일 ID/동일 파일 | 중복으로 판별 | 실행 수 증가 없음 |
| 동일 ID/다른 파일 내용 | 가져오기 거부 | 별도 판정 버전 명시 전 자동 병합 금지 |

중단·실패·부분 오류 항목은 상태를 넣은 fixture입니다. 프로세스 강제 종료·복구나 native eval의 순차 scorer 실패 시험은 아닙니다. 정상 점수와 미채점은 실제 `score()`로 생성하며, 부분 오류는 기존 점수에 합성 오류를 추가해 저장/읽기 보존을 검사합니다. 중복 기준은 M0에서 파일 SHA-256이며 의미적으로 같은 재직렬화 로그까지 중복으로 판별하는 기능은 M1 범위입니다.

Inspect 재채점은 native eval_id를 유지합니다. 따라서 원본 import 인덱스에 재채점 파일을 같은 원본처럼 다시 넣으면 내용 충돌이 됩니다. M1에서는 원본 evidence ID와 새 judgment ID를 분리하고 기준 버전·부모 판정·native eval_id를 연결해야 합니다. M0의 작은 import 함수는 그 제품 기능을 구현하지 않습니다.

재채점은 명시적으로 전달한 scorer와 `mockllm/model`을 사용하며 append 결과를 별도 파일로 저장합니다. 이전 파일 해시와 외부 실행 fixture 호출 수를 대조합니다. 이 경로에는 runtime 실행 핸들이 없습니다. 저장 로그의 endpoint·task 파일을 그대로 신뢰해 실행하는 범용 CLI 래퍼는 구현하지 않습니다. Inspect 전체가 비신뢰 코드의 격리 경계라는 의미는 아닙니다. `score()`의 평가 예외는 이번 경로에서 sample.error로 자동 변환되지 않고 ValueError로 전파됐으므로, M1 평가 어댑터가 별도 오류 판정으로 보존해야 합니다.

Inspect의 `TaskState.target`은 solver가 접근할 수 있습니다. 따라서 숨겨진 정답을 native Task의 target에 넣고 실행하면 입력 격리를 보장할 수 없습니다. M0는 외부 실행 fixture에 공개 입력만 전달하고 반환 후 평가 기록의 target에 비공개 canary를 넣습니다. 이는 fixture에서의 입력 분리 검사이며 임의의 runtime 입력 유출을 자동 차단하는 제품 기능은 아닙니다. 기존 runtime으로 전달할 입력과 평가 전용 기록을 분리해야 합니다.

## 기존 실행 경로 capability 대조

[별도 실행 기록](m0-runtime-results.json): 기존 Python 계약 검사 3개, Go 공통 요청 vector 26개가 통과했습니다. Go 1.26.11 공식 Windows archive의 SHA-256을 확인하여 작업 폴더에 설치했습니다. 전역 PATH는 변경하지 않았습니다. 설치 후 `runtime-workflow` 빌드를 실제로 시도했으나 `internal/control/server.go:177`의 `syscall.Flock/LOCK_EX/LOCK_NB` 미지원으로 실패했습니다. 이는 전체 실행 연동 성공이 아닙니다. Linux/macOS에서의 통합 검증이 남습니다.

runtime의 실제 go.mod는 codex-adapter `v0.0.0-20261119053648-3ab5b920bf6c`를 고정합니다. 위 adapter main 문서 검토 commit과 구별하며, 최신 main으로 의존성을 자동 갱신하지 않았습니다.

| 기능 | 현재 공개 계약/소스 | agent-eval 결정 |
| --- | --- | --- |
| 실행 소유권 | orchestrator가 흐름, runtime이 receipt/session, adapter가 Codex 통신 소유 | Inspect는 사후 평가만 담당 |
| 모델·인증 | adapter의 기존 Codex app-server·로컬 인증 | Inspect provider로 교체하지 않음; 실제 동일성 검증 M3 |
| 역할 세션·도구 | workflowmodel은 Task.Key() session, advisory tools 사용 | 원본 역할 식별자·프로필과 artifact 참조 연결 필요 |
| 기존 bridge v1 | 요청/응답 식별자·strict JSON·cache 통계 | Python 공개 validator와 양 저장소 공통 vector를 검사 |
| owner workflow | 별도 Unix socket control v1 | bridge JSONL과 동일 API로 간주하지 않음 |
| 작성→검토 인계 | producer receipt, artifact version/hash 확인 후 consumer 입력 생성 | 평가자는 실제 전달 문서와 hash를 별도 수집해야 함 |
| 임의 과제 주입 | live workflow producer는 소스의 고정 Brief 사용 | 설정 input 변경만으로 원하는 과제가 전달된다고 주장하지 않음 |
| 수정 루프 | 이전 pilot과 별개로 live workflow 자동 수정 없음 | M3 추가 구현 전 미지원 |
| 자료·도구 실패 주입 | live workflow 공개 제어 계약 없음 | M3 구현 전 실행 전 거부 필요; 현재 제품 gate 미구현 |
| 재시도·복구 | 성공 receipt 재사용, 실패/불확실 자동 재실행 금지 | 채점·import가 실행 재개를 호출하지 않음 |
| 토큰·비용 | workflow에서 null/미측정 | 0으로 변환하지 않음 |
| OS | orchestrator fcntl, workflow Unix socket | 현재 Windows에서 전체 경로 실행 검증 불가 |

근거: 고정 commit의 role-orchestrator `docs/protocol.md`, `docs/model-workflow-validation.md`, `role_orchestrator/workflow/{runner,client}.py`; role-runtime `internal/workflowmodel/executor.go`; codex-adapter `README.md`. 기존 저장소의 과거 모델 검증 보고서는 이번 실행 결과로 집계하지 않습니다.

**중요한 호환성 차이:** Inspect는 현재 입력/판정 계약을 수용할 수 있지만 기존 live workflow는 임의 과제 실행기가 아닙니다. agent-eval 과제를 전달하려면 고정 Brief를 버전 있는 과제 입력 계약으로 바꾸는 M3 작업이 필요합니다. 단순 Inspect solver 래핑으로 해결되지 않습니다.

## 과제 타당성과 제품 필요성

사용자는 현재 진행 중인 “무설치 직군 스킬 로딩 서비스 조사”의 과제가 부적절하여 결과도 적절하지 않다고 지적했습니다. 이는 사용자 제공 문제 제기이며, 해당 세션의 원문이나 결과를 이번 작업에서 독립 검증하지 않았습니다.

이에 따라 과제 타당성, 수행 성능, 평가 신뢰성을 별도 축으로 관리합니다. 과제에는 측정하려는 능력·실제 사용 상황·충분한 입력·허용 행동·판단 가능한 성공 기준·기준 사례·검토 상태를 기록합니다. 과제 타당성은 미검토/승인/반려로 구분하고, 미검토·반려 과제는 진단 실행은 가능하되 성능 우위·직무 적합성 결론을 보류합니다. 과제 변경은 새 버전이며 이전 실험 결과를 덮어쓰지 않습니다.

M0 fixture는 계약을 확인하기 위한 자료입니다. 직무 과제의 타당성이나 스킬 효과의 근거로 사용할 수 없습니다. 과제 타당성의 승인 기록과 사람이 확정한 기준 사례는 M2에서 검증하며, 현재 승인됐다고 표시하지 않습니다.

## 후속 Linux 실행 검증

위 Windows 빌드·실행 제약은 당시 기록입니다. 이후 사용자 승인에 따라 Docker/Linux 경로에서 기존 workflow와 Inspect의 실제 통합을 검증했습니다. 합성 19개와 실제 Codex 작성→검토가 통과했습니다. [환경·실패 이력·결과](m0-linux.md)를 참조합니다. Windows 네이티브 지원 완료를 뜻하지 않습니다.
