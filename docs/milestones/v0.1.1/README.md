# v0.1.1 · 개발 산출물 인계와 누락 원인 검증

**상태** Python 변경 과제 한 건의 목표 접수부터 최종 증거 인수까지 실모델로 통과했습니다. 기존 두 역할 인수와 최초 목표 접수 실패도 비교 기준으로 보존합니다. [새 실험의 증거](evidence/goal-case/README.md) · [직전 마일스톤](../v0.1.0/README.md)

## 목표부터 패치 인수까지

잘못된 유니코드 문자열을 읽는 JSON 파서 결함을 새 과제로 제출했습니다. 시작 입력은 목표·기준 Git 커밋·수정 범위였습니다. 독립 검사는 배정 전에 기준 실패를 확인하고 작성자와 분리했습니다. 오케스트레이터가 명부의 8명에게 총 13건을 배정했고 실제 입력 해시·담당자·영수증을 대조했습니다.

| 인계 | 관측한 결과 |
|---|---|
| 시나리오 → 동일성 → 중단 상태 → 검증 사례 | 기준 커밋의 소스로 사례를 작성했습니다. Go 변경 담당자의 배정은 0건입니다. |
| 사례 독립 검토와 보완 | 문자열 중간의 잘못된 문자도 검출해야 한다는 반례를 받아 사례를 수정하고 새 해시로 수락받았습니다. |
| 회귀 테스트 작성 → 제품 패치 작성 → 패치 검토 | 처음 검토의 계약 밖 판정값을 거절하고 같은 검토자의 정정 영수증을 받았습니다. 수락된 원본 두 diff를 적용한 커밋은 `401080b`입니다. |
| 격리 실행 → 증거 검토 | 독립 검사가 기준 실패·후보 통과했습니다. 같은 unittest 메서드 2개에서 기준은 하위 사례 단언 실패 24건, 후보는 모두 통과했습니다. 최종 검토자는 후보 커밋 증거를 요구했고 동일 Git 트리에서 재실행한 자료를 받은 뒤 미결 사항 없이 수락했습니다. |

이 과제에서는 사례 검토자가 반례 누락을, 증거 검토자가 빌드 식별자 누락을 발견했습니다. 패치 검토 단계에서는 검증기가 허용되지 않은 판정값을 거절했습니다. 동일성·중단 상태 역할은 현행 검증 사례 계약의 고정 의존성으로 호출됐습니다. 파서 변경에 대한 두 역할의 독립적 기여는 측정하지 않았습니다. 격리 실행은 별도 실행기가 수행했으며, 사용자 입력부터 병합까지 무인 운영하는 범용 개발 시스템은 이 실험의 검증 범위를 벗어납니다.

최종 오케스트레이터 `dd07d43`의 고정 이미지에서 전체 테스트 122건이 통과했습니다. 오프라인 재조회는 추가 모델 제출 0건, 실행 상태 파일 변경 0건이었습니다. [전체 검사](evidence/goal-case/controller-suite.json) · [오프라인 대조](evidence/goal-case/offline-replay.json)

## 최초 후보의 목표 접수 실패

고정 후보 이미지와 명부로 빈 상태에서 새 과제(한 번도 시작하지 않은 개발 과제의 상태 조회가 디렉터리를 만들지 않음을 검증하는 회귀 테스트 추가)를 제출했습니다. 기준 소스와 lab Git 저장소를 읽기 전용으로 제공했습니다. 두 시도 모두 공개 CLI의 development_case run과 codex 백엔드를 사용했습니다.

| 제공 입력 | CLI 종료 코드와 사유 | 새 상태 디렉터리 |
|---|---|---|
| case_id, goal, base_sha, source | 2 · invalid development case fields | 없음 |
| case_id, criterion.id, author 안의 goal·base_sha·source | 2 · invalid_role_fields:regression,acceptance,output_contract | 없음 |

두 실행 모두 역할 배정 전 입력 검사에서 종료됐습니다. 당시 진입점은 회귀 조건·인수 조건·출력 계약을 호출자에게 요구하며 작성자와 검토자만 순차 배정합니다. 명부에 등록된 다른 역할을 호출자가 직접 배정하는 실험은 자율 배정의 인수 근거가 될 수 없습니다. 후속 역할의 실행 품질은 이 재검증에서 측정되지 않았습니다.

## 목표

개발 책임자가 이번 인계 결함을 작업으로 주면, 오케스트레이터가 이름이 고정된 담당자를 런타임으로 실행해 반례, 변경 패치, 독립 검토 결과를 차례로 받습니다. 격리 실행기가 동일한 반례로 기준 커밋의 실패와 후보 패치의 통과를 확인하고, 검증한 패치와 적용 대상 SHA를 개발 책임자에게 반환하면 이 개발 경로가 완료됩니다. 병합과 릴리스는 기존 결정 절차를 따릅니다.

## 출발점과 원인 조사

11월 23일의 인계 구현과 테스트는 같은 커밋에 들어갔습니다. 당시 통합 기록은 단일 인계의 수정·수락과 재시작을 확인합니다. Git에 남은 공통 작성자와 M3 수락 표시는 개별 담당자의 배정 내용이나 검토 판단을 특정하기에 부족합니다. [구현과 테스트](https://github.com/shakystar/role-orchestrator/commit/2dfe5329047d7951c969eaf88fd7c5154f369a17) · [당시 수락 범위](../v0.1.0/README.md)

검증할 가설은 개별 작업의 성공 조건을 충족해도 다음 역할이 요구하는 산출물이 빠질 수 있었다는 것입니다. 네 발견별로 아래 순서를 복원합니다.

| 대조할 기록 | 확인할 질문 |
|---|---|
| 당시 역할 계약 → 실제 배정 입력 | 해당 작업이 읽기로 끝나는지, 후속 역할에 결과물을 제출해야 하는지가 지시에 명시됐습니까? |
| 제출한 산출물·패치 → 구현 커밋 | 어느 작업이 변경을 만들었고, 검토에 넘긴 개정과 커밋된 변경이 일치합니까? |
| 인수 사례 → 테스트 단언 → 리뷰 판정 | 누락을 드러내는 입력이 있었습니까? 테스트가 무엇을 관측했고 리뷰어가 어느 범위를 수락했습니까? |

다른 PC의 배정·검토 기록을 확보할 수 있으면 작업 ID와 개정 해시로 대조합니다. 발견별로 처음 확인된 누락 지점, 근거, 미확인 구간을 남깁니다. 원본이 없는 구간은 귀속 미확정으로 마감할 수 있습니다. 이후 실행에서는 배정 버전, 담당 멤버·작업 ID, 입력·출력 참조, 패치 해시, 검토한 개정, 판정 및 인수 기준 ID를 서로 연결합니다. 원문 대화나 인증 정보를 Git에 넣을 필요는 없습니다.

## 구현 계약과 인수 조건

| 항목 | 후보에서 관측해야 할 결과 |
|---|---|
| 역할 계약과 산출물 | 배정과 검증이 같은 버전의 역할 계약을 참조합니다. 결과 제출이 필수인 작업에서 빈 응답·잘못된 타입·필수 필드 누락은 완료를 차단하며 후속 제출은 0회입니다. 유효한 결과는 다음 작업의 입력에서 같은 개정·해시로 조회됩니다. 읽기로 끝나는 작업은 기존 방식으로 완료됩니다. |
| 보완 횟수 | 필수 필드 3개가 빠진 입력에서 현재 판별할 수 있는 누락을 첫 요청에 함께 담습니다. 담당자가 지적 사항을 모두 고치면 한 번의 보완으로 구조 검사를 통과합니다. 슬롯당 2회·실행당 6회의 한도와 의미 검토가 필요한 개정의 명시적 수락을 보존합니다. |
| 실패와 복구 | 요청에 결속된 확정 실패 영수증은 실패 사유와 함께 조회됩니다. 제출 여부가 불분명하거나 영수증이 유효하지 않으면 불확실 상태를 유지합니다. 두 경로 모두 재시작 뒤 묵시적 재제출은 0회입니다. |
| 보완 요청의 동일성 | 같은 요청 작업·대상·슬롯·기준 개정·인수 조건에서 관찰 문구만 바뀌면 기존 미결 요청을 반환합니다. 서로 다른 결함은 구분하고 서로 양립할 수 없는 수락 조건은 충돌로 남깁니다. 중복 요청 수와 추가 모델 제출 수를 따로 측정합니다. |
| 기존 기록 | v0.1.0의 완료·미결·불확실 기록을 후보에서 다시 읽습니다. 과거 완료의 근거와 기존 작업 키를 보존하고 조회로 새 실행이 생기지 않아야 합니다. |

## 작업 순서와 책임

파일별 구조 조사, 유지할 모듈 및 재검토 조건은 [모듈화 검토 기록](module-review.md)에 있습니다.

1. 시나리오·사례 담당자가 기준 커밋에서 네 발견을 재점검하고, 독립 검토자가 각 반례의 기대 결과를 구현 전에 고정합니다. 기존 의도와 양립하는 동작은 유지할 대조 사례로 등록합니다. [팀 명부와 역할 계약](https://github.com/shakystar/agent-collaboration-lab/blob/0bbd7b1/docs/features/development-handoffs.md)
2. 오케스트레이터 담당자가 역할 계약 적용, 산출물 저장·인계, 보완 요청 및 상태 판정을 구현합니다. 런타임 담당자는 기존 영수증으로 확인 가능한 실행 사실과 실패 분류를 대조하고 부족한 계약만 변경합니다. 기존 어댑터로 개발 과제를 수행하는 것을 기본으로 합니다.
3. 회귀 담당자가 고정 반례와 호환 사례를 실행합니다. 독립 검토자는 실제 패치와 검사 결과를 인수 기준별로 판정하고, 근거가 부족한 개정은 작성자에게 돌려보냅니다. 증거 담당자는 검토된 패치와 격리 실행기가 시험한 패치의 해시를 대조합니다.

v0.1.1은 네 저장소를 함께 검증한 통합 마일스톤 버전입니다. 실모델 검증은 한 결함을 대상으로 했습니다. 첫 패치의 구현을 후보에 반영했고, 단일 명령 경로에서 나온 두 번째 패치는 같은 반례를 통과하는 독립 산출물로 보존했습니다. 작성·검토 시도는 서로 다른 역할 세션이며 과제 ID와 패치 SHA-256으로 연결됩니다. 검토 수락과 격리 테스트 통과를 각각 기록했습니다.
