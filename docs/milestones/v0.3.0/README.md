## 개발 및 리뷰 비교

후보 실행 전 확정한 개발 대조 과제는 기존 test_development_acceptance의 패치·시험 실행 및 영수증 연결이고, 리뷰 대조 과제는 기존 test_review_team의 정상 최소 경로·자기 검토 차단·보완 시 최종 인수 중지다. 전체 fixture 회귀는 동결 기준과 최종 후보에서 각각 한 번 수행한다. 실패 시 진단 재실행을 별도로 표시한다. fixture의 분기 통과와 실모델의 결함 탐지율은 별개로 집계한다. 독립 검토에는 해당 사례의 기대 판정을 입력하지 않는다.

최초 제출·수정본·결과·거절 근거·소요 시간은 확보한 실행 기록에서 산출한다. 동일 과제의 비교 가능성, 최종 인수 통과 여부, 누락 관측값을 함께 기록한다. 품질 편차 조사용 추가 반복은 대표 사례당 1회까지로 잡고 M5까지 확보한 편차를 후속 v0.3.1에 넘긴다.

## 통합 인수 시나리오

- 팀과 목표만 주어진 명확한 과제에서 필요한 인력이 선택되고 검증된 영수증이 남는다.
- 의도에 따라 범위가 달라지면 사용자 확인 또는 원작성자 보완 단계로 돌아간다.
- 기획팀이 직접 만든 연구팀 계약을 개발팀·리뷰팀이 독립적으로 인계받고 개정 및 근거를 추적한다.
- 의뢰 기반 연구와 선제 신호가 모두 기획팀의 근거 있는 제품 결정에 도달한다. 반증과 근거 부족도 보존한다.
- 기존 필수 경로와 재조회 계약이 유지된다. 제품 품질 편차는 관찰하되 필수 인수 실패와 구분한다.

## M5 통합 검증과 v0.3.1 인계

고정 후보 c3e777f, 실행 명부 ce998e9, 기존 Go 브리지로 합성 자료를 실제 모델에 전달했다. 의뢰는 관찰·초안·독립 검토·종합·기획 결정의 5단계, 선제 신호는 기획팀의 검토 착수 판단을 포함한 6단계를 거쳤다. 완료된 두 실행의 네이티브 영수증 11건을 각각 다시 확인했다. 동일 상태 재조회에서 결과와 체크포인트가 같았고 작업 키당 Go 실행은 1회였다. 연구팀의 보완 요청은 패킷에 수신자·누락 항목으로 남긴다. 실제 외부 원작성자에게 메시지를 발송하는 기능은 이 인수에 포함되지 않는다. ### 재현

아래 예시는 오케스트레이터 후보를 체크아웃한 작업 디렉터리에서 실행한다. LAB은 명부 Git 저장소, BRIDGE는 M0에서 해시를 기록한 런타임 브리지, CASES는 이 문서 옆 cases 디렉터리다. STATE는 현재 사용자가 소유한 새 디렉터리여야 한다. 고정 명부의 두 목표는 실행 호스트 UID 501에 위임됐다. 다른 운영 환경은 해당 사용자에게 위임한 별도 명부 개정과 그 해시를 사용한다.

```sh
mkdir -m 700 "$STATE"
python -m role_orchestrator.research_handoff --state "$STATE" --lab "$LAB" \
  --revision ce998e9031bb420ea13ebbaa9c2a3d3fa2d681dc \
  --catalog-sha256 07740a6559664d6ace4f6c6fd8dad328432bca3c73d2b640f556801d9c0994f7 \
  --runtime "$BRIDGE" --research-goal study --planning-team planning --planning-goal intake \
  --backend fixture < "$CASES/request-fixture.json"
```

신호 검증은 새 STATE에서 signal-fixture.json으로 실행한다. 실모델은 backend를 codex로 바꾸고 request-live.json 또는 signal-live.json을 사용한다. 기존 상태 조회는 같은 인수와 빈 표준입력을 사용한다.

### 팀 성능

M2·M4의 제품 코드 과제 2건 중 첫 제출로 수락된 건수는 0건이었다. M2는 코드 산출물이 있는 3개 개정, M4는 2개 개정을 거쳤다. 모델명·실행 프로필의 불일치, 상태 디렉터리 검증, 실모델 출력 형식과 미확인 근거의 인계에서 재작업이 발생했다. 리뷰팀은 이전·현재 후보에서 동일한 결함 사례를 각각 1/1 적발하고 정상 사례를 각각 0/1 오반려했다. 이 적은 표본에서 버전 간 성능 우열을 판정하지 않는다. 코드 모델이 생성한 산출물의 첫 제출과 인프라의 모델 미시작을 구분했다. [측정값과 후속 연구 대상](quality-baseline.json) · [국소 실행 시간 및 시도별 영수증](team-measurements.json)

v0.3.1에서는 실패 전후 계약과 산출물 차이를 근거로 리팩토링 필요성을 결정하고, 첫 제출 품질과 최저 사례를 미공개 동등 과제로 재측정한다. 이번에는 운영 시장 효과와 반복 가능한 최고 품질을 미측정으로 기록한다.
