# v0.3.3 · 하위 모델에서의 역할 계약 비교와 코드 품질 개선

**상태** 기획. 기능 구현, 신규 모델 실험과 운영 명부 변경은 미실행이다. [기획 이슈 #37](https://github.com/shakystar/agent-eval/issues/37) · [통합 마일스톤](https://github.com/shakystar/agent-eval/milestone/6) · [프로젝트 보드](https://github.com/users/shakystar/projects/2)

## 목표와 범위

1. 오케스트레이터가 역할별로 승인된 모델과 추론 수준을 지정하고, Sol 아래의 명시적 후보를 런타임과 어댑터에 전달할 수 있게 한다. 첫 대상은 연구팀 독립 검토자 배지안(acl-025)이다. 요청한 경로와 실제 세션·턴의 모델·effort가 일치해야 채점한다.
2. 같은 하위 모델 안에서 현행 계약과 후보 계약을 비교한다. 계약 간 차이가 관측되지 않을 때 다음 후보에서 재검토하는 조건을 미리 정한다. 운영 계약과 기본 모델 선택은 독립 판정 전까지 현행을 유지한다.
3. 기존 개발팀 산출물의 코드 리뷰 근거를 정책 조항과 연결하고, 라우팅 경계를 견본 모듈로 완성한다. 담당자가 바뀌어도 입력 정규화, 오류 반환, 상태 소유권과 회귀 사례의 위치를 찾을 수 있어야 한다.

v0.3.2 M4에서 변경한 변수는 한 계약의 추론 수준이었다. 양쪽이 모두 통과한 공개 두 사례와 이전 Sol 보정은 이번 비공개 평가의 분모에 합산하지 않는다. 모델 파라미터 수나 가격 서열은 모델명에서 추정하지 않는다. 후보는 gpt-6-luna, 조건부 후속 후보는 gpt-5.6-luna로 두며 실제 가용성·허용 effort·비용 근거와 첫 번째보다 더 낮은 체급이라는 전제가 확인돼야 두 번째를 그 용도로 사용할 수 있다. [직전 실험](../v0.3.2/M4-results.md) · [연구 및 기술 실사](연구와-기술실사.md)

## 동일 모델에서 두 역할 계약 비교

**표본과 통제** 명확한 요구, 미확정 의도, 관측·추론 혼합, 중요 오류 독립 검증을 주 유형으로 합성 사례 각 2건, 총 8건을 제안한다. 대표 업무·제외 기준, 두 계약 버전, 사례별 기대 사실·중요 오류·필수 보완 요청과 심각도를 사전에 고정한다. 모델 ID·effort·입력·도구 권한·캐시 조건을 같게 하고 계약만 교체한다. 현행 먼저 4건, 후보 먼저 4건으로 배분하고 독립 판정자에게는 계약명과 실행 순서를 가린 채 출력 제시 순서를 섞는다.

**호출 상한** 사례·계약당 1회, 계약별 8회, 라운드당 16회다. 최초 1라운드와 조건부 추가 진단 1라운드를 합쳐 최대 32회다. 실패 시도도 포함하고 자동 재시도하지 않는다. 추가 진단도 같은 사례를 쓰므로 고유 사례는 8건이다. 기술 인수 호출은 별도 예산 승인 전에는 실행하지 않는다.

**절대 기준** 조건 원장·양쪽 출력·필수 산출물·독립 판정 근거가 있는 유효 쌍 8/8이 필요하다. 계약별로 중요 오류 누락 0/8, 네 품질축 전체의 중요 오류 0건이어야 한다. 근거 없는 단정, 관측·추론 혼동, 필수 보완 요청 누락은 비중요 결함일 때 축별 최대 1/8이다. 같은 사례의 같은 축은 한 번만 세고 원시 오류 건수는 별도로 보존한다.

**우위와 미결정** 양쪽 모두 절대 기준을 통과하고 한 계약이 모든 사례·축에서 악화 없이 서로 다른 2건 이상에서 개선될 때만 파일럿 우위 신호로 기록한다. 유효 쌍 부족, 절대 기준 미달, 개선·악화 상충, 개선 사례 2건 미만은 우위 미결정이다. 절대 기준 미달은 해당 계약의 미통과로도 남긴다.

**중단** 중요 오류 1건, 한 계약의 비중요 축 하나에서 결함 사례 2건, 비교 조건 불일치, 종단 간 전달 실패 또는 호출 상한 도달 시 추가 호출을 중단한다. 확보한 자료만 판정하고 무효 쌍이나 미실행 사례를 무결함으로 세지 않는다.

**추가 진단 진입** 8/8 유효 쌍, 양쪽 절대 기준 통과, 중요 오류 0건, 8사례×4축의 짝 판정 불일치 0/32를 모두 만족할 때만 검토한다. 다음 조합의 능력·가격 순서, 종단 간 수락 및 시험 권한을 확인한 뒤 모델 ID 하나만 한 단계 바꿔 두 계약을 재비교한다. effort 대체가 별도 허용되면 모델 ID는 고정한다. 조건이 하나라도 확인되지 않으면 현행을 유지한다.

**운영 결정과의 경계** 0/32 불일치는 진단 진입 조건이지 동등성 증명이 아니다. 실질적 무차이를 주장할 때만 각 주요 지표의 짝 차이 추정 구간이 사전 합의한 동등성 한계 안에 있고 양쪽이 절대 기준을 충족해야 한다. 정밀도가 부족하면 미확인이다. 운영 하향은 무차이 확인 후 선택 계약을 고정한 별도 한 단계 시험, 기준 위반 시 직전 설정 복귀 조건, 독립 인수와 명시적 운영 결정이 필요하다.

## 개발 준비와 역요청

기준표와 성공·실패 벡터가 고정되면 Python과 Go 변경은 병렬 진행할 수 있다. 독립 인수팀은 모델 실호출 없이 블라인드 채점과 영수증 대조를 병렬 준비한다. 공용 계약을 변경하는 변경안과 동작 보존 리팩터링은 커밋 또는 PR을 분리해 독립적으로 되돌릴 수 있게 한다.

- 개발팀은 모델 ID나 effort 지원의 출처가 불명확하면 기획팀에 정확한 조합과 근거를 요청한다. 계정에서 호환 모델이 보이지 않으면 미지원 상태로 남긴다.
- 검증팀은 결과 파일 수와 실제 턴이 일치하지 않거나 요청 설정만 확인되면 개발팀에 해당 슬롯의 원장과 실행 근거를 요청한다. 기존 슬롯을 자동으로 다시 제출하지 않는다.
- 리뷰팀은 ‘스타일 불일치’만 적힌 항목을 원작성자에게 돌려보낸다. 정책 조항, 고정 소스 위치, 구체적 유지보수 영향, 기존 호출자 동작과 전후 검증법이 있어야 반영 또는 근거 있는 유지 결정을 내릴 수 있다.
- 연구팀은 고유 사례·반복 횟수·효과 범위가 불명확하면 인수팀에 분모를 재요청한다. 운영 채택이나 동등성 주장은 별도의 대표 표본과 사전 허용 범위를 요구한다.

개발 전 계약 소유 레포의 `docs/features/`에서 기능 명세와 공용 사례 개정을 연결한다. 통합 계획 및 추적은 이 디렉터리와 GitHub Project에서 관리한다. 적용 정책은 [공통 개발 정책](https://github.com/shakystar/agent-collaboration-lab/blob/112d4629d4261b4403ff33fbde43e36431c435f4/docs/development-policy.md)과 [기능 명세 양식](https://github.com/shakystar/agent-collaboration-lab/blob/112d4629d4261b4403ff33fbde43e36431c435f4/templates/feature-spec.md)이다.

## 마감 판단

단계별 현재 검증 결과는 모두 미실행이다. 기획 근거는 [팀별 산출물과 영수증](planning-evidence.json)에 보존한다. 운영 채택은 별도 결정으로 남긴다. 하위 모델 제공자 확인 실패, 불완전한 대응쌍, 개선 근거 부족은 각각 미확인 또는 현행 유지로 기록한다. Docker 복구 [#35](https://github.com/shakystar/agent-eval/issues/35)와 에이전트 컨텍스트 메모리(v0.4.0)는 별도 범위다.
